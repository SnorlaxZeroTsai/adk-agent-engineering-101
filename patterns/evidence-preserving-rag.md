# Evidence-Preserving RAG

Status: candidate pattern, observed in Phase 5 local/scripted experiments.

## Problem

A RAG answer may be factually plausible while retrieval exposed an
unauthorized, stale, deleted or uncitable source. Response-only evaluation
cannot distinguish these failures.

## Context

Use this pattern when an Agent answers from managed Search, Vector Search, a
custom index or any retrieval service where source lifecycle and citations
matter.

## Architecture

```text
versioned source + ACL
  -> ingestion + reconciliation + deletion
  -> retriever applies ACL before top-k
  -> structured hits retain source/version/chunk/URI
  -> model answers only from hits
  -> citations reference those exact hits
  -> evaluator checks retrieval, lifecycle, answer and citations separately
```

Managed and explicit retrieval may use different adapters. They share the
evaluation contract, not necessarily one runtime interface.

## Invariants

Each hit retains:

- document ID and version;
- chunk ID;
- source URI or stable locator;
- authorization attributes;
- content;
- index/embedding version where applicable.

Each query case defines:

- principal;
- expected document IDs;
- expected facts or abstention;
- allowed citation sources.

## Forces

- Managed services reduce ingestion code but hide some indexing behavior.
- Explicit pipelines increase control and reconciliation responsibility.
- More metadata increases result size but enables governance and debugging.
- Native grounding is compact in the Agent trajectory but provider-specific.
- FunctionTool retrieval is inspectable but normally adds a model round trip.

## Implementation

1. Version source, parser, chunker and index schema.
2. Give every chunk a deterministic ID.
3. Apply access filters before ranking and top-k.
4. Return structured hits, not anonymous formatted text.
5. Require no-hit abstention.
6. Cite source/version IDs from the current retrieval response.
7. Reconcile obsolete versions and deletions explicitly.
8. Gate retrieval recall/precision, ACL, stale/deleted hits and citation
   fidelity independently of final-response quality.

## Failure Modes

- ACL expressed only in prompt text.
- Filtering after top-k, which can leak or suppress authorized results.
- Chunk text returned without source identity.
- Incremental create without old-version deletion.
- Source deletion without index/cache reconciliation.
- Citation URLs generated by the model rather than copied from evidence.
- Generic LLM-judge score with no expected retrieval IDs.
- Treating native Search and FunctionTool fallback as identical trajectories.

## Counterexamples

Do not add a retrieval system when a small, deterministic and frequently
updated lookup belongs in a normal database/API tool.

Do not use citation formatting as a substitute for provenance. A syntactically
valid citation can still reference an unauthorized or deleted source.

## Trade-Offs

- More ingestion and evaluator code.
- Stronger auditability and reproducibility.
- Larger structured tool responses.
- Explicit delete/re-index operational burden.
- Easier comparison of managed and explicit backends on the same dataset.

## Evidence

Lab 05 observed:

- 5/5 grounded baseline cases on native managed and explicit paths;
- native path: one model request and grounded metadata;
- explicit path: two model requests and FunctionTool evidence;
- correct answer with zero citation recall after provenance stripping;
- correct current answer with one stale hit;
- public retrieval of one internal source without filter;
- resurfacing of one deleted promotion without index reconciliation.
